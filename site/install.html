Deployment guides

Install TelltaleDNS

Pick where it runs. Every path ends the same way: your router hands out TelltaleDNS as the DNS server, and every device on the network uses it, with its own address visible.

  • Raspberry Pi (Docker Compose) — the recommended home setup
  • Raspberry Pi or Linux (native, systemd)
  • Kubernetes (Helm)
  • A Pi and Kubernetes together
  • Point your network at it · Troubleshooting

Guide 1 · about 10 minutes

Raspberry Pi with Docker Compose

  1. Prepare the Pi. Raspberry Pi OS (64-bit recommended) on a Pi 3, 4, 5, or Zero 2 W, with a fixed address (set a DHCP reservation in your router), and Docker: 
    curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER    # log out and back in
  2. Free port 53. If Pi-hole or another DNS server runs on the Pi, stop it. Check: sudo ss -ulpn 'sport = :53' should print nothing.
  3. Download the bundle and start it. 
    mkdir ~/telltale && cd ~/telltale
curl -fsSLO https://raw.githubusercontent.com/paimonsoror/telltaledns/main/deploy/compose/compose.yaml
curl -fsSLO https://raw.githubusercontent.com/paimonsoror/telltaledns/main/deploy/compose/telltale.toml
docker compose up -d
docker compose ps        # STATUS shows "healthy" within a minute
  4. Test it from another computer (replace the address with your Pi's): 
    dig @192.168.1.2 example.com          # an address: it resolves
dig @192.168.1.2 doubleclick.net      # 0.0.0.0 or NXDOMAIN: the blocklist works
    On Windows: nslookup example.com 192.168.1.2.
  5. Create the admin account. Print the one-time setup token and open the UI at http://<pi>:8053/: 
    docker compose exec telltale telltale auth setup-token
  6. Point your network at it: see below.

Updating: docker compose pull && docker compose up -d. Editing the config: change telltale.toml, then docker compose kill -s HUP applies it without dropping a query. On an SD card, the starter config keeps the query log for 7 days; a USB SSD is better for longer history.

Guide 2

Raspberry Pi or Linux, native

No Docker: a single static binary as a sandboxed systemd service. The installer checks the release's signature and checksum before installing anything, so read it, then run it:

curl -fsSLO https://raw.githubusercontent.com/paimonsoror/telltaledns/main/deploy/systemd/install.sh
less install.sh
sudo sh install.sh --edge          # without --edge: the latest tagged release
sudo -u telltale telltale auth setup-token -c /etc/telltale/telltale.toml
  • It asks first: press Enter for the recommended settings, or walk me through the options to pick upstreams (encrypted presets or your own server), starting blocklists (or none), the listen address, the first admin (a setup token, or a password now), and the query log's retention and privacy. Every step shows its default; Enter keeps it. Piped or automated runs (and --yes) ask nothing.
  • It creates a telltale user, writes the config to /etc/telltale/telltale.toml (never overwriting yours), and keeps data in /var/lib/telltale.
  • If systemd-resolved holds port 53 (Ubuntu, some Debian setups), it asks to turn the stub listener off.
  • Updates: sudo telltale self-update --restart (add --channel edge if you installed with --edge). The previous binary is kept as telltale.old.
  • Logs: journalctl -u telltale -f. Reload after editing the config: sudo systemctl reload telltale.

Guide 3

Kubernetes with Helm

helm install telltale oci://ghcr.io/paimonsoror/charts/telltale --devel \
  -n telltale --create-namespace \
  --set service.dns.annotations."metallb\.universe\.tf/loadBalancerIPs"=192.168.1.53
kubectl -n telltale get svc telltale-dns     # EXTERNAL-IP: your DNS server address
kubectl -n telltale exec telltale-0 -- /usr/local/bin/telltale auth setup-token \
  -c /etc/telltale/00-chart.toml -c /etc/telltale/10-values.toml
  • Every option: helm show values oci://ghcr.io/paimonsoror/charts/telltale --devel > values.yaml prints the chart's commented values file; the Helm values reference lists each key with its default and meaning. Keep what you change in your own file and pass it with -f.
  • Chart versions: every build from main publishes 0.1.0-edge.N, which is what --devel picks; pin one with --version instead.
  • Keep externalTrafficPolicy: Local (the default): with Cluster, every query looks like it came from a node, and TelltaleDNS shows a "client IPs appear masked" banner.
  • Your settings go in config: (TOML, the same keys as the configuration reference); secrets come from existing Secrets.
  • Encrypted DNS for phones: encrypted.dot.enabled / encrypted.doh.enabled with a cert-manager certificate.
  • Monitoring: serviceMonitor.enabled, prometheusRule.enabled, grafanaDashboard.enabled.

Guide 4 · clustering

A Pi and Kubernetes, one cluster

Nodes can already form a cluster and keep an mTLS link: telltale cluster init --name home --advertise https://192.168.3.2:8443 on the first node, telltale cluster token create there, then telltale cluster join tt_join_… on the other. Only the first node's port 8443 must be reachable; the others connect out. The first node's configuration and blocklists then reach every node within seconds (signed, and only what changed), and each node keeps answering from its last copy if the link drops.

  • One management plane. Any node's UI shows the whole cluster's dashboard and query log, and changes made there go to the primary.
  • Failover. Promote another node by hand (telltale cluster promote), or let the cluster elect one (telltale cluster set-failover auto) once it has a third voter, such as a tiny witness (telltale cluster witness).
  • Node-local settings. Each node keeps its own listeners, retention, and overrides; everything else is shared.
  • More pods in Kubernetes. mode: scaled adds resolver pods beside the controller (resolvers.replicas). They join on their own, share the DNS Service, leave the cluster when they shut down, and keep answering for a few seconds while the Service drops them, so rollouts don't lose lookups. For one address for DNS, the UI, and the cluster port, set service.dns.alsoServe.
  • See it. The Cluster page draws the cluster live: sites, the primary, pods grouped by Kubernetes node, link round trips, and each node's share of the queries.
  • Git as the source. Optionally, the shared configuration can come from a Git repository or a GitOps tool (config_source = "gitops").
  • Maintenance. Rolling upgrades work across one version step (N and N−1), and telltale cluster rotate-ca replaces the cluster's certificate authority without downtime.

Details: the running guide, clustering sections.

Coming from Pi-hole?

Bring your Pi-hole setup with you

  1. In Pi-hole, open Settings → Teleporter and click Export (v6 gives a .zip, v5 a .tar.gz).
  2. Run telltale import pihole pi-hole_teleporter.zip -o pihole.toml. It carries over your upstreams, conditional forwarding, local DNS and CNAME records, adlists, allowed and denied domains (exact and regex), groups, clients, and DHCP reservations as named devices.
  3. Read the notes at the top of pihole.toml: they list everything that has no equivalent (for example clients matched by host name, or the DHCP server). Then add the file to your configuration.

Query history and passwords aren't imported. Keep Pi-hole running until TelltaleDNS answers the way you expect, then point your router at TelltaleDNS.

Coming from Technitium? Create an API token in Technitium (Administration → Sessions), then run TECHNITIUM_TOKEN=… telltale import technitium http://your-server:5380 -o technitium.toml. Forwarders, zones and records, forwarder zones, block lists, Advanced Blocking groups, and DHCP reservations come across. The notes at the top of the file list the rest.

Last step

Point your network at it

  1. In your router's DHCP (LAN) settings, set the DNS server to TelltaleDNS's address (the Pi, or the LoadBalancer IP). If there's a second field, use a second TelltaleDNS, or leave it empty: a public resolver there lets devices skip your blocking.
  2. Renew leases: reconnect Wi-Fi, or wait for leases to expire (often a day).
  3. Open the dashboard: devices appear under Clients with their own addresses. Give them names and groups there.

Don't point the router's own upstream DNS at TelltaleDNS while devices use the router: every query would then come from the router, and TelltaleDNS would say client IPs appear masked.

If something's off

Troubleshooting

"address already in use" on port 53
Another DNS server runs there: Pi-hole, dnsmasq, or systemd-resolved's stub (sudo ss -ulpn 'sport = :53' names it). Stop it, or for systemd-resolved add DNSStubListener=no under [Resolve] in /etc/systemd/resolved.conf.d/telltale.conf and restart it.
A site is broken
Find it in the Query log and press Why?: it names the list and line that blocked it. Then add an allow rule for it (an @@||name^ line in a list, or an allowlist).
Every query shows the same address
Something in between rewrites addresses: a router forwarding DNS, Docker without host networking, or Kubernetes with externalTrafficPolicy: Cluster. The UI's banner says which address; the client IP guide has the fixes.
Lost the setup token
telltale auth setup-token prints it again until the first admin exists.
