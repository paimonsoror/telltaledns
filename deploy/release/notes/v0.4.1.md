A small fix release for clusters: every node now names a device the same way.

## Fixes

- **Device names are the same on every node.** In a cluster, usually only one node reads your router's client list (the one with its API key), and pods can't hear mDNS. So the query log named a device ("living-room-tv") in that node's rows and showed only its address in the other nodes' rows, and resolver pods' anomaly findings and device identities missed the router's names too. Now every node asks the others once a minute for the names their routers and mDNS learned, and uses them after its own. Within a minute of starting, a resolver pod names devices exactly as the primary does, without the router's credentials. The cluster query log also names any row that reaches it without a name.

## Upgrading from 0.4.0

- Nothing to change. Once every node runs 0.4.1, the names line up. A node still on 0.4.0 keeps naming its own rows as before, and the others skip it when they ask for names.
- If your resolver pods carry a `[[router]]` block they can't read (no credentials mounted), it still logs one warning at start. You can drop it from their configuration: they now get the names from the node that reads the router.
- Order of names, unchanged for a single node: the name you gave a device, then this node's routers, then this node's mDNS, then the other nodes' routers and mDNS (the primary's first).

## Known issues

- **DNSSEC `validate` mode:** right after a start, an upstream that closes fresh DoT connections can make the first validations fail, so a signed name may get SERVFAIL until its keys are cached. Keep `permissive` or `off` for now; see ADR-098.
- `_dns.resolver.arpa` (encrypted-DNS discovery) is forwarded upstream instead of being answered locally.

## For developers

- New ADR: 125 (device names are shared across the cluster). New cluster call `devices.names`.
