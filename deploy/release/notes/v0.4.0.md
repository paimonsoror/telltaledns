An operations release: try a change against your real traffic before you make it.

## Highlights

- **What would this have done?** Before you save a quick rule, a list, a group change, a device move, or an upstream change, replay the query log with it: the queries of the last day are decided again with and without the change, and you see what would have been newly blocked, newly allowed, sent to another upstream group, or answered differently, by name, device, and group, with the rule or list that decided. Only the changed lists are compiled, and DNS never waits for it. It's a button in the UI, `simulate=24h` on any dry run, `POST /api/v1/simulate` and `telltale config simulate` for a whole configuration (test a Git commit before pushing it), and `simulate_change` for agents. In a cluster every node replays its own log. Agents' plans simulate only when they ask, unless you turn on Settings → System → Change simulation → "Agents' plans simulate by default".

- **What is this device?** The Clients page says what each address looks like ("Looks like a Roku player"), from its maker (the IEEE registry), the name it announces, and the domains it talks to, scored against a catalog of 45 common home devices that ships with TelltaleDNS. The guess fills in the naming form, and a group that lists the kinds of device it's for (`device_classes = ["camera", "plug"]`) gets suggested for them. Nothing is named or moved on its own; set "What it is" on a device to correct it. Agents get `identify_device`.

## Upgrading from 0.3.0

- **Agent tokens:** simulating needs the `querylog:read` scope as well as the change's own. A new scope, `config:write:simulate`, changes the simulation settings.
- **Upgrading a cluster:** mixed versions work together; a node on 0.3.0 doesn't take part in simulations and is listed under `missingNodes`. Upgrade replicas first, then the primary.
