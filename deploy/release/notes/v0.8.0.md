A release for people who run clusters: a support package that covers every node, a cluster whose trust in its certificate authority only moves forward, elections that rarely need a second round, reads that can't tie up a node, routers you add in the web UI, devices named by their MAC address that keep their rules when they get another address, and, as an experiment that is off by default, upgrades driven from the cluster. Also new: domain icons, "not" filters in the query log, and quick rules that fill in what a rule can use; the upstreams of a `parallel` group now each wait for their own answer. It also tightens what a user below administrator can ask a node to run or read: see **Security**.

## Highlights

- **A support package for the whole cluster.** `telltale support-package --cluster` asks every node for its part and returns one `.tar.gz`. Each node redacts its own data before it leaves, under one key for the whole package, so the same device or name has the same pseudonym on every node. A part that is slow, fails, or is cut for size is marked in the manifest (`missing` or `truncated`, with the reason) and the rest is complete; a node older than this feature is listed as missing. Nothing is uploaded: you read it first.

- **Domain icons.** A brand tile or a monogram beside each domain in the top lists and the query log. The icons ship in the binary (Simple Icons, plus Bootstrap Icons for marks Simple Icons dropped) and nothing is fetched from the internet. **Settings → Account → Domain icons** has the options.

- **Search for what doesn't match.** The query log's name, client, status, type, and response-code filters each have a "not" form: "does not contain", "is not", "does not match regex", and so on. It works in the web UI (the Match menu and a "not" box beside Client, Type, and Rcode), in `GET /api/v1/queries` (`nameNot`, `clientNot`, `statusNot`, `qtypeNot`, `rcodeNot`), in `telltale qlog search` (`--not-name` and the like), and in the agent tools. A negated name or client search can't skip blocks by their bloom filter, so give it a time range on a long log. During a rolling upgrade a negated search of the whole cluster reaches only the upgraded nodes; an older node is listed as not reached and never answers it wrongly. See ADR-171.

- **Offline UniFi clients get their names.** A device that is off right now is named from the console's client history and your configured clients, so the query log stops showing a bare address for a phone that is simply asleep. `offline_days` on the `[[router]]` entry (30 by default; 0 names only connected clients) and a cap of 1,024 bound it, and an offline client doesn't count as "seen". From Carlos Talbot's pull request.

- **Routers in the web UI.** **Clients → Discovered → Routers → Add router** adds or edits a UniFi or OPNsense router and takes its API key as a paste. The node saves each pasted value in a file only it can read (`secrets/router-<name>.<key>.<random>` in the data folder, mode 0600), never shows it again, and sends it only to the router address and settings it was entered with. A change takes effect within 5 seconds after the reads in progress end, without a restart. Only an administrator adds, changes or removes a router (an agent token never can); the API takes the key itself and never a path (`PUT`/`DELETE /api/v1/routers/{name}`); a pasted key needs `https://` (or a loopback address). A pasted key is not in backups and is not copied to other nodes: after a failover or a restore you paste it again, while a key kept in `/run/secrets/` or `/etc/telltale-secrets/` on every node needs no re-entry. Everyone else sees each router's status (key saved, missing, or not used), not its key files or user name. From Carlos Talbot's pull request. See ADR-181.

- **Devices named by their MAC address follow it, from your routers' lists.** A device you named by its MAC (`match = ["aa:bb:cc:dd:ee:ff"]` in a `[[client]]`, a MAC client from the Pi-hole importer, or **Name this device…**) is now also recognized at the address your router reports for that MAC (UniFi's connected clients, OPNsense's DHCP leases), on the node that reads the router and on the full cluster members that hear from it. The kernel's neighbor table still comes first. So the device keeps its name, groups and rules when it gets another address, also where the kernel can't see it: rootful Docker's bridge network, Kubernetes with the chart's `externalTrafficPolicy: Local`, another VLAN. **Name this device…** offers the MAC when it knows it, can save the device by its MAC alone, and edits the device an address is already recognized as instead of making a second one. A router's MAC isn't used for an offline client, for a MAC at two or more addresses, for a row the router isn't sure of, or once a router (or another member) has been silent for 15 minutes; while a device is named by its MAC, each router is read at least every 10 minutes. The routers' lists are IPv4 only. Explain and `identify_device` say how an address was recognized (`router_mac`) and where its MAC came from. New setting `[clients] router_macs` (default `true`). What changes for existing installs is under **Upgrading**. See ADR-183. From Rajackar's report (#73).

- **Quick rules from the query log fill in what a rule can use.** **Why? → Make a quick rule** fills in the device TelltaleDNS recognizes at the address, else the address itself, and shows the name the log gives it beside it ("shown in the log as …"): a name your router or mDNS gives a device is a label, and a rule can't be for it. A Kubernetes pod starts as a rule for its group only when an operator placed its workload in one. The form checks the rule as you type (a dry run, 400 ms after the last change) and shows a refusal before you save; Save stays available. The API's refusal of such a device now reads "`X` isn't a named device (`[[client]]`), an IP, or a CIDR", with a hint that names the address that name belongs to (an agent token without `querylog:read` gets the plain hint). What a rule accepts is unchanged. From Rajackar's report (#73).

- **Upgrades driven from the cluster: experimental, and off by default.** From Greg Pakes's pull request (#72), with changes made on top. See ADR-182 and **Upgrading from the cluster** in the running guide.
  - **What it does.** A native node (installed with `install.sh`) can be asked to install a newer signed release or edge build of its own channel. The node only writes a request; a separate root service (`telltale-update.path` and `telltale-update.service`) verifies the signature and checksum, installs the build, restarts the node and checks the node's own API address (`/readyz`). If the new build doesn't answer ready twice within 120 s, it puts the previous binary back (`rolled_back`). A slow or failing `systemctl restart` is left to that check.
  - **Turning it on,** per node: `sudo sh install.sh --cluster-updates`; on a node on edge builds `sudo sh install.sh --edge --cluster-updates` (or `--stable` to move it to releases). It refuses a binary folder that isn't root's alone (older Debian and Raspberry Pi OS images have `/usr/local` as `root:staff 2775`: check with `stat -c '%U:%G %a' /usr/local /usr/local/bin`, fix with `sudo chmod g-w /usr/local /usr/local/bin`), a data directory under `/home` or `/root` or in a folder that isn't root's, a node with the API off, and a node that doesn't answer at its health address (it prints the address it tried).
  - **The channel is the node's setting.** A node on releases takes only releases; a node on edge builds takes edge builds and newer releases, and stays on edge. An edge node's update service installs whatever main's CI signed last.
  - **`telltale ctl upgrade --to <version>`** (or `--to-self`) checks every node first, then upgrades the native nodes one at a time, replicas first and the primary last. A node is done only when its update service reports the version installed and healthy and the node is back on it, ready and in sync; a failure or a rollback stops the run. `--timeout` is 15 minutes per node; `--skip-down` leaves out only nodes that are down; every request carries `X-Telltale-Reason` (`--reason`). Witnesses and containers are left alone; pods are the chart's.
  - **The Helm chart's `upgradeHook`** (off by default) runs `ctl upgrade --to-self` before the pods roll (a PreSync hook in Argo CD). It needs a Secret with an agent token (`analytics:read` and `cluster:upgrade`) before the sync that runs it, a pinned `image.tag`, and `helm upgrade --timeout 45m` or more (and as long for Argo CD's sync). `whenUnavailable: fail|skip` decides what happens when a pinned edge build has been replaced; `upgradeHook.caSecret` is for a self-signed `https://` API.
  - **`telltale self-update --to <version>`** installs one version by hand, a release or the newest edge build, and can go back to an older one.
  - Treat it as experimental until you have watched it upgrade, and roll back, a node of yours: nothing has yet upgraded a real node between two published builds. What to check first is under **Upgrading**; the limits are under **Known issues**.

- **A smaller image.** The images are about 13 MiB compressed on each architecture, down from about 14.8. The OpenAPI document is compiled in, the embedded web UI is gzip-only, the zoneinfo is compact, SQLite is built without full-text search, R-tree and dbstat, and the crates that are not on the DNS path are built for size. What the image does is unchanged.

- **Trust in the certificate authority only moves forward.** A node takes a certificate authority change only from a manifest that is no older than the last one it took, so a replayed or late manifest can no longer bring a retired authority back, or undo a step of a rotation in progress. Replicas, witnesses, and resolver pods keep that mark in `cluster/ca.version`, beside `ca.crt`; a mark from another cluster is ignored, and a build that doesn't know the file ignores it. If a primary's version ever goes backwards (its saved state was lost), trust and configuration wait until it passes the mark: promote another node, or stop each node and delete `cluster/ca.version`. See ADR-177.

- **Certificate-authority rotation, hardened.** A key share and a trust change on a replica can no longer interleave (it could leave a stray `ca-old.key`, a few percent of the time on a two-CPU machine); the primary's rotation step takes the same lock; each file a rotation writes has its own temporary file, and the CLI's `ca-next.key` is owner-only from its first byte. A witness now verifies manifests against the authority it trusts now, so after a rotation it keeps saving the registry and the failover mode instead of freezing until it restarts, and it logs, and renews its certificate once.

- **Elections that don't split.** When a primary goes away, two nodes freed by the same lease end used to ask for votes at nearly the same instant and split them, which cost another 15-second lease. A node that grants a pre-vote to a node that sorts before it now gives that node the round. In a three-voter cluster the model needs no second round in 200,000 runs (mean 13 s to a new primary), and real-process runs took one round every time. Clusters with more voters split less often but not never, and a lost or late message, a restart, or a disagreement over the epoch can still cost a round. See ADR-178.

- **A read that waits for other nodes can't tie up a node.** A cluster read from the web UI or the API used to wait on a runtime worker; on a replica with few workers, enough of them at once could stall the node's API, metrics and cluster port. They now wait on an operating-system deadline, outside the runtime. The number of calls a read can have outstanding is budgeted (32,768 in all, 4,096 for one read, 32 reads waiting), and the bytes of the answers a read holds are bounded (20 MiB for one read, 40 MiB in all). A read that is refused, or kept only in part, is counted in `telltale_federated_refused_total{reason}`, logged once a minute, and shown as partial. See ADR-174 and the Upgrading section.

- **Break-glass is visible.** The sign-in page and Settings now say when password sign-in is restricted to listed networks (`passwordLoginRestricted` on `/api/v1/auth/status`; administrators also see the networks and whether they cover a whole network or loopback). `telltale config check` warns when break-glass is on with an empty network list, start-up says so in the log, and a request from a same-host proxy that isn't in `[api] trusted_proxies` leaves one hint line, at most every ten minutes, because behind such a proxy every browser looks like 127.0.0.1. The default is unchanged through 0.x. The two-factor code box now takes a code. See ADR-175.

- **Lists.** The chart's `TelltaleDNSListStale` alert fires only for a list whose last good copy is over 48 hours old and whose latest refresh failed, so a long `refresh_secs` or a list you disabled while healthy no longer pages. New: `TelltaleDNSListNeverLoaded`, for a list that has never loaded (a typo in a new list's URL), after an hour. A disabled list is left out of the `telltale_list_*` metrics. An inline list whose rules are refused is tried once and again when you change it, instead of retrying many times a second with a log line and a disk write each time. From Greg Pakes's pull request.

- **A replica forgets a peer it keeps no link to** once that peer has been silent, so a replica that was removed from a cluster no longer shows as "down" in the metrics and `/api/v1/system/info` for ever. From Greg Pakes's pull request. See ADR-173.

- **Installing.** `install.sh` waits up to 15 seconds (`TELLTALE_PORT_WAIT`, a number from 0 to 300) for port 53 to be free before it starts the service, ignores the service's own sockets, and starts it once. Zero-padded answers in the guided setup (`08`, `007`) mean the number they spell. **Get started** now leads with the native install for a Raspberry Pi or Linux; Docker Compose sits under Docker. OPS-004 says so: the installer and systemd unit are the primary path.

- **The watchdog says more.** A dump now says how the runtime is doing; when the restart cap is reached and the node is still stuck, the dump and the log say so (once an hour while it lasts), and `telltale_watchdog_restart_cap_reached_total` counts it. A scrape can't reach a stuck node, so alert on `up == 0`.

## Security

Our own review found that earlier releases let a user below administrator, and an agent token, ask a node to run a program or read a local file through the API, the web UI, MCP and a replica's forwarded writes. This release closes those routes. If only administrators change your configuration, nothing changes for you beyond the rules below.

What earlier releases accepted, from anyone who could change configuration (the operator role, and agent tokens with `config:write` scopes):

- **A program as an upstream.** An upstream or a forwarded domain whose server was `exec://<program>` (with `args`) made the node start that program and keep it running; `unix://<socket>` made it connect to a local socket. A draft check (`POST /api/v1/checks/upstream`) could start the program for a few seconds.
- **A credential file for an alert destination.** `token_file` and `password_file` could name any file the service can read; the content went to the destination's own address as a bearer token, a Gotify token or an SMTP password.
- **A local file for a list, or for a simulation.** A list's `path` could be chosen by an operator, and since 0.4.0 a viewer's change simulation could name list, zone, hosts and TLS files; the error text of a list, a check or a test send could quote part of the file.
- **A simulation's downloads.** A simulation fetched lists under the candidate's own link-local setting, size cap and timeout, with no limit on how many, so a viewer could make every node fetch and hold a lot of data.

From this release:

- **Plugin upstreams (`exec://`, `unix://`, `args`) are defined in the config file only.** The API, the web UI, MCP and the draft check refuse them for everyone, administrators included; plugins in the config file or the Helm values work as before. One already stored through the API is left out of the running configuration (the log names it); define it in the config file and delete the stored one with `DELETE /api/v1/upstreams/<name>`. The rest of your API-made configuration stays in effect.
- **A credential file on an alert destination made through the API is an administrator's choice, and must be in a place meant for secrets:** `/run/secrets/`, `/etc/telltale-secrets/` or `<data_dir>/secrets/`. An agent token, an administrator's too, can't set one, and an operator can't edit a destination that has one. The folders that platforms project for a pod's identity (`kubernetes.io`, `eks.amazonaws.com`, `azure`) don't count, and neither do the files that keys pasted into a router live in. On every node, a destination that names a credential file is sent only if its file is in one of those folders or the node's own config files (or its Git commit) define it the same way; otherwise it is skipped, and the log, the Alerts page and **Send test** say why. Destinations in the config files and the Helm values keep any path.
- **A list's `path` through the API needs an administrator** (their own sign-in or an administrator's API token). Callers below administrator see a generic reason in place of what reading a local file went wrong with, on the Lists page, in the health reason, in the `list_failing` alert, in a check and in a test send. A change simulation by a caller below administrator can't name a local file, program or socket that the running configuration doesn't already name.
- **Simulations fetch under this node's own limits:** its link-local setting, byte cap, timeout and compile limits, for every caller. A simulation reads at most 4 changed lists, within 4 × `max_list_bytes`; past that it answers 422 (a dry run's preview says `download_limit`). A change that touches more than four lists at once can't be simulated whole. The node's one-simulation-at-a-time slot now covers the downloads too.

**What to do:** upgrade, then check the audit log for `upstream.put`, `forward.put`, `alert_destination.put` and `list.put` by users who aren't administrators and by agent tokens. If you let someone else write alert destinations, replace the credential the destination's file held. Review each API-made destination that has a credential file, and each API-made list that has a path.

**Not covered, and why:**

- **Clusters.** The primary plans every write, so these rules hold once the primary runs this version. Entries an older primary already published stay in the replicas' and a promoted primary's configuration, and keep working there (a plugin keeps running) until the older primary's entry is replaced; see ADR-180 for how. The usual order (replicas first, then the primary) leaves a short window; upgrade the primary promptly, then run the checks above.
- **A destination stored by an older version that names another secret inside one of the three folders** is still used: the folders bound where a file may be, not which secret it is.
- **`http://` destinations with a credential file.** On a node that resolves through TelltaleDNS itself, anyone who may add local names or forwards can change where the destination's host resolves, so a token sent over `http://` can be sent to another address. Use `https://` (or `smtps://`) for a destination with a credential file.
- **Small leftovers**, all in ADR-180: an email destination's `tls_ca` error on the Alerts page, the size and line counts `GET /api/v1/lists` shows for a file list, and the fact that a valid TLS file builds where a bad one doesn't.

See ADR-179 and ADR-180.

## Fixes

- **DNSSEC `validate` mode: unsigned zones under NSEC3 Opt-Out parents.** With `[dnssec] mode = "validate"` (opt-in; the default is `off`), a delegation is accepted as unsigned only when the proof is made of the validated records of the delegation's own parent zone. This now also proves unsigned delegations under NSEC3 Opt-Out parents such as `.com`, `.net` and `.org`, which the earlier proof could not do. A zone proven unsigned is remembered per upstream group for its proof's TTL, at most 15 minutes. See ADR-184 (Proposed). From Michael Roughton's pull request #74 and our review of it.
- **A stop or a reload while a node is starting** (SIGTERM, SIGINT, SIGHUP from `systemctl reload`, SIGUSR1) used to end the process, because the signal handlers were installed after DNS already answered. It is now acted on once the node is up: a drained stop, a reload, a list refresh. A stop during a cluster join ends the join and stops the node at once.
- **A group with one upstream** no longer SERVFAILs a name its upstream takes unusually long to answer: the last healthy member may use the rest of the 2 s budget (#35). Attempts still running when a query ends finish in the background and are counted, so an upstream that stops answering is benched after three timeouts in a row: until then each query waits up to 2 s for it, and after that up to its `timeout_ms` (400 ms by default) while it stays silent. A name an upstream takes longer than 2 s to answer counts as a timeout too: three in a row, with no answer from it in between, bench even a healthy sole upstream for 10 s (doubling while its probes fail). See ADR-165.
- **`strategy = "parallel"`: each upstream asked at once waits for its own answer.** Every member with a closed breaker among the first `parallel_fanout` may now use the rest of the budget, like the last member above, so a name the faster one has to look up itself is answered by it instead of being cut off at about 3 × its usual time + 50 ms and counted as its timeout. The cost: a racing member that goes silent is benched after about 2 s instead of almost at once (in a local test at 100 cache misses a second, after 2.0 s instead of 79 ms, with up to 201 attempts to it outstanding instead of 44, while clients got the other member's answers in a few milliseconds), and until then a client whose other member answered SERVFAIL or REFUSED waits for it, up to 2 s, then up to its `timeout_ms`. From Michael Roughton's pull request #76 (issue #75). See ADR-165.
- **An upstream whose `timeout_ms` is under 20 ms** no longer stops the node when it is asked: the hedge delay is then that timeout.
- **`self-update` and the update service** try a freshly downloaded binary's test run again (up to five times, 100 ms apart) when the system says the file is still busy ("text file busy"), instead of refusing it as a binary that doesn't run.
- **A replica attached to another replica** moves back to the primary (#43); blobs are fetched from the primary only.
- **Heatmap and Dashboard charts** keep every node's data (#61); the minute-grain 7-day heatmap no longer loops.
- **List hits** are counted across the cluster and by name, allows included.
- **Change simulation:** the default window includes the request's own second; `until=now` means the default end; the support package's query sample includes the newest second (#69).
- **The wall** keeps its panel when its area is measured again (#69).
- **`state.db`:** two processes opening a new file at the same moment now apply each migration once (a replica could lose the race and disable its API).
- **Inline lists** report no last-success time they never had.
- **Dependencies:** rusqlite 0.43 (the SQLite it builds is unchanged), the `url` crate 2.5.9 (RUSTSEC-2026-0592), jiff 0.2.46, and minor and patch updates of bytes, clap, rand, regex-automata, syn and xxhash-rust.

## Upgrading from 0.7

Most installs need no change. Check these if they apply to you:

- **Clusters: upgrade replicas first, then the primary, and don't leave the primary waiting.** Two reads are new on the wire, the query log's "not" search and the cluster support package; a node that doesn't know one is listed as not reached for it (and never answers it wrongly) until it is upgraded. A forwarded write now carries one more field (`by_admin`, left out when false, so an older primary sees the same bytes as before). The trust, election, and read-budget changes are inside each node. The Security section's rules hold once the primary runs this version, so run the checks listed there right after it does. Also new on the wire, and ignored by an older node: the call that asks a node for an update (an older node answers "unknown call"), marks on the device-name answers and their router rows that say which bindings can identify a device (an upgraded node takes none from an older member), `recognition` in an identity (an older entry node ignores it), and a refusal's fuller hint beside its plain one (an older node shows the plain hint).
- **Devices named by a MAC address get their rules in more places.** Where a `[[client]]` matches by MAC (by hand, or from the Pi-hole importer) and a router reports that MAC at an address the kernel's table doesn't hold (Docker's bridge network, Kubernetes, another VLAN), the device now gets that `[[client]]`'s groups and rules instead of its address's, network's or `default`'s. This starts on every upgraded node that reads a router, or that hears from a full member that does. In a rolling upgrade it starts once the node that reads the router (usually the primary) runs this version. Devices not named by a MAC aren't affected. To keep the old behaviour, set `[clients] router_macs = false`, after every node is upgraded.
- **`[clients] router_macs`** (new, default `true`) is shared by the cluster and applied on reload. It is written into what the primary shares only when it is `false`: an older replica refuses a shared configuration that has it (`shared configuration: unknown field …`, and keeps serving the last one it had), and an older build won't start with it in its own file. Set it to `false` only after every node is upgraded, and remove it before you go back to 0.7.
- **Every node now reads the kernel's neighbor table** (every `neighbor_refresh_secs`, 60 s, while `[clients] neighbor_table` is on, the default), whether or not a device is named by its MAC. `telltale_neighbors` counts the kernel's entries, so it is no longer 0 on nodes without such a device.
- **Routers and MACs in a cluster.** What a router says reaches only the nodes with a direct stream to the node that reads it: a replica's router reaches the primary (and, under automatic failover, the other voters), while a resolver pod hears only the primary and gets the primary's own router view. So put the router's key on the primary, and on the node a failover would promote. If the reading node goes away, devices named only by their MAC fall back to their address, network or `default` 15 minutes later; a key pasted in the UI stays on the node that saved it. If devices are named by MAC and no router MAC reaches a node, its log says so once, after a minute.
- **The 15-minute bounds.** A router silent for 15 minutes, or a member whose answer is older than 15 minutes, identifies nothing until it answers again. While a device is named by its MAC, each router is read at least every 10 minutes (600 s) whatever its `interval_secs`, and a failed read is retried every 15 seconds.
- **A MAC address can be copied.** A device that copies a named device's MAC is that device. For an allowance worth protecting, use a client ID (DoT or DoH). A block on a device named only by its MAC applies only while the MAC is vouched for (a private Wi-Fi address that changes, an extender that shares one MAC, 15 minutes of router silence, or a restart sends the device back to its address, network or `default`): put a restriction you must enforce on its network's group. A router's list now decides which rules a device gets, so check its certificate (`tls_ca`, `tls_server_name`) rather than `tls_insecure_skip_verify`; the node logs a warning when a router whose certificate isn't checked starts to recognize devices.
- **Agents and MAC addresses.** An agent token with `config:read` (not limited to a group) can read the MAC of any address it asks about, through `identify_device` and explain: the same MACs the device keys in `GET /api/v1/clients` show. A token with `analytics:read` alone, a token limited to a group, and a display session get the rest without the MAC, and explain leaves the MAC out at query-log privacy level 2 and above unless the caller gave it. The routers' lease list (`/api/v1/dhcp/leases`) stays closed to agents.
- **Upstreams.** A sole upstream that stops answering now costs a query up to 2 s (not 70 to 400 ms) until three timeouts in a row bench it, and in a `parallel` group a racing member that goes silent is benched after about 2 s instead of at once: see Fixes.
- **Upgrades driven from the cluster, the first time.** A node without the feature can't be asked: upgrade each native node by hand once, on its own channel (`sudo telltale self-update --restart`, with `--channel edge` on a node on edge builds), then run `install.sh` again for the units (with `--cluster-updates` to turn them on; on an edge node always with `--edge`, since without it `install.sh` installs the newest release and sets the stable channel). Until then `ctl upgrade` names the node and says to upgrade it by hand.
- **`rolled_back` is an incident signal, not proof the build was bad.** The node's own process answers the health check, and any local user can take the API port during the restart, so look at the node (`journalctl -u telltale -u telltale-update`) before you ask again. A build that was installed and didn't come up is held back on that node for 24 hours (`update_failed_recently`, shown as `held`, with until when); a failure in the downloads holds nothing back. With the chart's hook on, a hold blocks every Argo CD sync on that pin for up to a day: move the pin, install by hand with `self-update --to`, or wait.
- **The hook's token.** A token that expires or is revoked, or `[agents] enabled = false`, fails every sync from then on, a values-only `helm upgrade` too: make it without an expiry, or rotate it in time. On a first install, keep the hook off or create the Secret with a placeholder (a missing Secret fails the hook at once). A node upgraded from the cluster restarts without a maintenance window, so a `node_down` alert can fire for a moment.
- **Plugin upstreams made through the API stop being used** (a log line names each); define them in the config file. **API-made alert destinations whose credential file is outside `/run/secrets/`, `/etc/telltale-secrets/` and `<data_dir>/secrets/` stop sending** until an administrator saves them again with a file in one of them. **On a replica, or a node promoted after a failover, a destination from the primary's config file whose credential file is outside those folders isn't sent** unless that node's own files define it the same way (not an issue with the Helm chart: every pod mounts one ConfigMap). See Security.
- **Routers and native clusters:** router key files outside `/etc/telltale-secrets/` and `/run/secrets/` are no longer read on replicas or on a primary promoted after a failover, unless that node's own config file (or the Git commit it uses) defines the same router with the same key file and address, or the key was pasted in the UI on that node. ADR-120 used to suggest `/etc/telltale/...`: move the key under `/etc/telltale-secrets/<router>/` on every node. A node that holds a router back logs a warning that says why, and a replica's Routers page shows the primary's status, not its own. Single-node and Helm installs are unaffected. In a cluster, upgrade every node before adding routers in the UI: an older primary refuses a router change a replica sends it.
- **Routers made in the UI,** restored from a backup, or edited in `state.db` may name only a key pasted in the UI on that node, or the very key file and address the config file gives that router. An entry that names any other file outside the data folder's `secrets/` (for example an override that kept the config file's key after the config file moved or removed that router) is left out, with a warning, and the config file's router, if any, is used. One that names a file in `secrets/` the node didn't save for that router and address stays in the configuration but isn't read, with a warning.
- **Router config files:** `site` is now sent percent-encoded as one path segment (every character but letters, digits, `-`, `.`, `_` and `~` is escaped, a slash or a percent sign included), and `{site}` inside `url` is no longer replaced: give the address in `url` and the site in `site`. A `url` set through the API may not contain `{` or `}`.
- **Configuration writes through the API:** a retry with the same `Idempotency-Key` while the first request is still running gets 409 `change_in_progress` with `Retry-After`; a node runs at most 32 changes at once (a 33rd gets 503 with `Retry-After`; dry runs aren't counted); and a change whose client disconnects now runs to its end and is audited. Every write route documents the 409 and the 503.
- **The longest cluster reads can come back partial.** On a cluster of three or more nodes, `GET /api/v1/stats/timeseries` for 7 days of minutes or 400 days of hours exceeds the byte cap and lists the nodes it left out in `missingNodes`. The dashboard's own ranges are far under it. Narrow the `scope`, use a coarser `step`, or ask for a shorter range. The web UI's ranges are unchanged.
- **A new file on replicas, witnesses, and resolver pods:** `cluster/ca.version` (about 60 bytes). Going back to 0.7 is harmless: the old build ignores it.
- **Prometheus rule users:** the chart's list alert has new text and a new meaning (see Lists), and `TelltaleDNSListNeverLoaded` is new. `telltale_list_*` no longer includes a list that is switched off.
- **Metrics added:** `telltale_federated_refused_total{reason="waits|spent|ceiling|bytes"}`, `telltale_watchdog_restart_cap_reached_total`, `telltale_router_macs{source="router|peer"}` and `telltale_router_macs_unsure`. `telltale_neighbors` counts the kernel's neighbor table only (see above).
- **API:** `GET /api/v1/auth/status` has `passwordLoginRestricted`; `GET /api/v1/users` gives administrators a `passwordLogin` block; `PUT`/`DELETE /api/v1/routers/{name}` are new (administrators only), and `GET /api/v1/config/entries?kind=router` shows each router's key status. The cluster's CA-step manifests are unchanged. `GET /api/v1/nodes/{id}/update` (a node's version and update state; viewers, and agent tokens with `analytics:read`) and `POST /api/v1/nodes/{id}/update` (`?dryRun=true`; an administrator, or an agent token with the new `cluster:upgrade` scope, which is in no default set and never given to an OAuth sign-in for MCP) are new, with seven `update_*` problem codes listed in the running guide. `GET /api/v1/clients/{address}/identity` and the agent tool `identify_device` gain `recognition` (`device`, `identifiedBy`, `mac`, `macFrom`, `macShared`, `macRandomized`); explain gains `client.macFrom` and the `identifiedBy` value `router_mac`. A rule's device that isn't a named device, an IP or a CIDR is refused (422) with the new text above and a hint; a script that matches the old text ("is neither a device name nor an IP or CIDR") needs the new one (anomaly mutes keep the old text).
- **`install.sh`** (a fresh install or a re-run) now waits for port 53 and starts the service once. It also installs `telltale-update.path` and `telltale-update.service` and leaves them off, and its readiness wait asks the address taken from `[api]` (with the default config the same `127.0.0.1:8053` as before; with the API off it asks systemd). `self-update` takes `--to <version>`, and tries a freshly downloaded binary's test run again while the file is busy.

## Known issues

- **A process hang (#7).** The mechanism the reporter's analysis pointed to is fixed (a cluster read can't hold a runtime worker), but the cause of the original incident is not proven, so the issue stays open. If it happens again, attach the watchdog dump under `<data_dir>/watchdog/` or a support package.
- **The Cluster page, `/api/v1/health`, and the in-app `NodeDown` alert** still list a replica that the metrics and `/api/v1/system/info` have forgotten, as "down, no link" (ADR-173).
- **Failover in an unusual partition.** When a node that sorts first can reach some peers but can't win, the model's worst case for a new primary is about 35 seconds (it is 24 without the tie-break); a three-voter cluster keeps its 13-second mean.
- **The byte cap bounds the peers' answers only.** This node's own part, and several long-range reads merging at the same moment, aren't bounded by it (ADR-174), so a Raspberry Pi serving two very long ranges at once can still use a lot of memory.
- **Two certificate-authority manifests that share one version** can still replace each other, which needs a crash or a failed save during a rotation and someone holding both signed manifests; ADR-177 records the fix (a digest in `ca.version`) as not built.
- **DNSSEC `validate` mode:** right after a start, an upstream that closes fresh DoT connections can make the first validations fail, and a name queried before its parent zone's keys are cached can fail for up to a minute (it works again after that minute). Keep `permissive` or `off` for now; see ADR-098.
- `_dns.resolver.arpa` (encrypted-DNS discovery) is forwarded upstream instead of being answered locally.
- **Routers made in the UI.** Changing a router from an API key to a username and password keeps the old key in use (remove the router and add it again). An override the merge leaves out shows only in the log, not as a row. A router pinned to a version from before a key was replaced reads "key missing" while it is pinned.
- **Upgrades driven from the cluster** (experimental):
  - If `systemctl` itself fails without restarting anything (its binary missing, or a refusal on the system bus), the old process still passes the health check: the run is recorded `updated` while the old build runs, and the next request for that version answers `up_to_date`. Check `journalctl -u telltale-update` and run `sudo systemctl restart telltale` on the node. Comparing the node's process before and after the restart is planned.
  - A node that takes longer than 120 s to come up (very large lists on an SD card) is rolled back: upgrade it by hand.
  - `--cluster-updates` refuses a data directory under `/home` or `/root` until the request moves to a folder only root owns (planned).
  - A native primary whose replicas are the chart's pods would be upgraded before them by the hook: run `ctl upgrade` by hand in that shape. On some CNIs (Cilium) a controller that is up but not ready makes the hook fail rather than skip; with the controller dead, turn the hook off to roll a fix.
  - No MCP tool and no Cluster page button yet.
- **Devices named by their MAC address:**
  - The routers' lists are IPv4 only: a device named only by its MAC is recognized in its IPv6 queries only through the kernel's NDP table.
  - A device named only by its MAC isn't covered by its group's anomaly mutes, change previews and simulations, the Clients page's guess of what it is, or identity and rhythm look-ups by name.
  - A router read only by a replica doesn't reach the resolver pods (passing it on is a follow-up).
  - In a cluster that spans sites reusing one private range, a member at another site can bind a local address to a MAC: keep such a cluster on one site's routers, or set `router_macs = false`.
  - An address reused within one router interval (300 s by default) gets the old holder's rules until the router's next answer, and up to a minute more on the other nodes.
