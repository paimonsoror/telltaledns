A hardening and visibility release: a full review of the observability, clustering, and API layers, a dashboard for every node, acknowledgeable anomalies across the cluster, and one health icon for the whole deployment.

## Highlights

- **Health at a glance.** An icon at the bottom of the menu says whether everything is working: healthy, degraded (an upstream or node down, a device rate-limited, a list failing, a disk filling up), or severe (no upstream in a group answering, DNS not served). Click it for each reason, its node, and where to look. The same answer is at `GET /api/v1/system/health` and in the MCP tool `health`.
- **Anomalies for the whole cluster, and a way to clear them.** The Anomalies page now shows every node's findings, including those of Kubernetes resolver pods, and anomaly alerts see them too. **Acknowledge** a finding once you've looked: it stops counting as new on every node, including one that was down at the time. Operators can do it from the UI, the API, or an agent with the new `ops:anomalies` scope.
- **The dashboard, node by node.** **Showing** switches between every node together, one node, or one site. Top clients show their groups.
- **Upstream failures by kind.** Each upstream's failures are split into timeouts, connection errors, bad replies, SERVFAIL, REFUSED, and more, in the API and the Upstreams page. A run of SERVFAIL or REFUSED answers alone no longer marks an upstream as dead.
- **Tunable limits.** The per-client rate limit can be changed from the UI, the API, or an agent. TCP, DoT, DoH, and DoQ listeners cap connections per client address. The advertised EDNS size is configurable (`[dns] edns_payload`).
- **Tighter clusters.** A join token now decides whether the node it brings may be promoted (`--eligible`) or is a witness (`--witness`), instead of the joining node. Join tokens can be listed and revoked. Only voters can fence a primary. Election leases use a clock that never steps. A Git-managed node takes over from an emergency primary by itself.
- **Tighter API.** Password checks are bounded, a list check doesn't echo what it fetched, configuration writes run one at a time, admins can revoke other users' API tokens, and promotion from a signed-in session asks for the password and code.
- **Maintenance mode.** Before swapping a Pi's SD card or moving a box, put the node in maintenance (Cluster page, `telltale ctl maintenance start`, the API, or an agent with `ops:maintenance`): for a set time it reports not ready, so load balancers move away, keeps answering whatever still arrives, and is left out of alerts, the health level, and elections. The primary hands its role to another node first under automatic failover.
- **Privacy levels cover everything.** Levels 1 and up now also govern the live analytics, the stored top lists, and the anomaly engine. Level 1's name hashes are keyed with one key per cluster.

## Upgrading from 0.2.0

Most installs need no change. Check these if they apply to you:

- **Joining eligible nodes and witnesses:** create the token with `telltale cluster token create --eligible` (or `--witness`). A join with `--eligible` on a plain token is now refused. Nodes that already joined keep their roles.
- **Behind a reverse proxy or ingress:** `X-Forwarded-Proto` is trusted only from `[api] trusted_proxies` (or loopback). If the UI is served over HTTPS through a proxy, set `trusted_proxies` to its network so sign-in cookies stay `Secure`.
- **One client address with many TCP, DoT, DoH, or DoQ connections:** each listener allows 32 per address by default (`max_connections_per_address`; `0` for no limit). Raise it behind a load balancer that hides client addresses.
- **Lists with more than 1,000 regex rules:** the extra rules are left out of the snapshot and reported on the Lists page. Raise `[filter] max_regexes` if you need them.
- **List URLs on link-local addresses** (169.254.0.0/16, fe80::/10, cloud metadata) are refused unless `[filter] allow_link_local_urls = true`.
- **Audit log:** entries older than `[auth] audit_retention_days` (365 by default; 0 keeps everything) are trimmed hourly, with a checkpoint so the chain still verifies. If the audit log can't record, changes are refused with 503 instead of going unrecorded.
- **Privacy level 1 and up:** the anomaly engine is off at these levels. At level 1, names hashed before the upgrade don't group with names hashed after it, because the hash is now keyed.
- **The setup token** is no longer written to the log. Print it with `telltale auth setup-token`. Cluster members other than the primary don't create one.
- **Scripts reading `/readyz`:** the status codes are unchanged (200 ready, 503 not); the body is now JSON with the reason (`{"ready":false,"reason":"maintenance"}`) instead of `ready`/`not ready`. The Helm chart's startup probe asks `/readyz?startup=1`.
- **Upgrading a cluster:** mixed versions work together. Upgrade replicas first, then the primary.

## Known issues

- **DNSSEC `validate` mode:** right after a start, an upstream that closes fresh DoT connections can make the first validations fail, so a signed name may get SERVFAIL until its keys are cached. Keep `permissive` or `off` for now; see ADR-098.
- `_dns.resolver.arpa` (encrypted-DNS discovery) is forwarded upstream instead of being answered locally.
